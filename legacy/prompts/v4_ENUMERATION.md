# Промпт v4 — перепись единиц (enumeration)
Проект BURATINO · 2026-07-15 · альтернатива v3 для A/B-сравнения
Готовое тело: **`gemini_vision_jsonBody_v4.json`** (меняются systemInstruction И response_schema).

---

## 1. Механизм (чем v4 принципиально отличается от v3)

v3 менял только текст промпта — итог по наблюдениям: чуть лучше, но недосчёт количества и подвидов остался. Причина глубже текста: при temperature 0 и JSON-выводе у модели нет «черновика» — она вынуждена выдавать готовые числа сразу, а VLM считают плотные ряды «на глаз» плохо.

v4 встраивает черновик в саму схему ответа:

1. **Поле `units` — перепись.** Модель обязана выписать КАЖДУЮ единицу переднего ряда отдельным элементом: `{shelf_index, unit_index (слева направо), brand, subtype}`. `propertyOrdering` гарантирует, что units генерируется ДО items — считать «на глаз» структурно невозможно, число = длина списка.
2. **`items` — агрегация переписи.** Группировка по (полка, бренд, подвид), `front_facing_count` = число элементов группы. Контроль: сумма по items = длина units.
3. **Подвид решается per-единица, а не per-группа.** Каждая банка рассматривается индивидуально («не копируй subtype от соседа») — бьёт по недочитанным подвидам: в v2/v3 модель вешала один подвид на всю группу.
4. **Шпаргалка признаков возвращена** (компактнее, чем в v2, по строке на подвид): v3 показал, что PDF без текстовой опоры подвиды не вытягивает. Приоритет при конфликте прописан явно: справочник главнее шпаргалки.

Трейд-оффы: ответ длиннее (≈25 токенов на единицу; полка на 50 единиц ≈ +1300 токенов вывода) — дороже и медленнее на несколько секунд. Риск ленивой переписи (модель схлопывает повторы) прижат явным unit_index и правилом «один физический объект = один элемент».

## 2. Совместимость с n8n — правок нод НЕ нужно

«Парсинг обработки Google Vision», «Подготовка данных…» и «Формирование результата» читают только `items` / `overall_confidence` / `notes` — поле `units` они молча игнорируют. Схема items не менялась.

Бонус для отладки: в executions теперь видна перепись — по units сразу понятно, ГДЕ модель потеряла единицу или перепутала подвид (полка + позиция). На регрессии это заменит ручное разглядывание.

## 3. Установка

1. Нода «Gemini Vision (3.5-flash)» → JSON Body → заменить содержимое на `gemini_vision_jsonBody_v4.json`, сохранив ведущий `=`.
2. То же в fallback «Gemini Vision (3-flash-preview)».
3. `propertyOrdering` — поле Gemini structured output. Если API вернёт 400 (не поддерживается на этой версии) — удалить оба `propertyOrdering`, порядок обычно следует порядку properties в схеме; units стоит первым и так.

## 4. A/B-протокол (сравнение v3 vs v4 на нескольких фото)

Одни и те же фото прогнать через оба варианта, фиксировать по каждому фото:

| Метрика | Как мерить |
|---|---|
| Сумма единиц по фото | Σ front_facing_count vs ручной подсчёт — главная |
| Ошибки бренда | строки с чужим/перепутанным брендом |
| Подвиды | % верных / % ошибочных / % null (ошибочный хуже null) |
| Внутренняя консистентность v4 | длина units = Σ front_facing_count? если нет — модель нарушает контроль |
| Латентность и output-токены | `_usage` в парсинге уже пишется |

## 5. Если и v4 не дотянет — следующие рычаги (по одному за раз)

1. **`media_resolution` в generationConfig** — повышенное разрешение обработки изображений; мелкие крышки/этикетки на дальних полках читаются лучше. Синтаксис и поддержку для gemini-3.5-flash проверить по докам generateContent (поле появилось в API в 2025; если 400 — просто убрать): `"media_resolution": "MEDIA_RESOLUTION_HIGH"` в generationConfig. Дороже по input-токенам за фото.
2. **Thinking-режим**, если у 3.5-flash есть управляемый бюджет рассуждений (thinkingConfig) — это тот же «черновик», но нативный. Проверить по докам; сочетается с v4.
3. **Два прохода** (счёт отдельно, подвиды отдельно) — отклонили из-за ×2 цены, вернуться только если единый промпт упрётся в потолок.
