# Промпт v3 — реструктуризация (счёт → подвиды)
Проект BURATINO · 2026-07-14 · заменяет системный промпт из `gemini_vision_jsonBody_v2.json`
Готовое тело: **`gemini_vision_jsonBody_v3.json`** (схема и contents не менялись, только systemInstruction).

---

## 1. Диагноз: почему v2 просел по бренду и счёту

Симптом (наблюдение Никиты, одно и то же фото): v2 хуже v1 считает количество, путает бренды, считает лишнее/недосчитывает.

Причины в структуре v2:

1. **Правила подсчёта уехали в конец.** В v1 блок «ПРАВИЛА ПОДСЧЁТА» шёл сразу после задачи. В v2 между задачей и правилами — ~60% промпта (21 описание подвидов + «не путать»). Основная задача потеряла вес, модель «думает о подвидах», когда должна считать.
2. **Два источника истины.** Словесные описания подвидов (цвета этикеток/крышек) дублируют справочник-PDF. Любое расхождение (оттенок на реальном фото ≠ слову в тексте) — конфликтующий сигнал, сомнение протекает на уровень бренда.
3. **Потеряно ключевое правило v1:** «явно наш бренд, но вкус не читается — считай, снизь confidence». В v2 осталось только «не уверен в бренде — не считай» + строгие правила подвидов. Итог: строгость по подвидам выбивает единицы из счёта → недосчёт.
4. **Дробление на подвидовые группы без контроля суммы.** Считать per-подвид сложнее, чем per-бренд: ошибка разбиения = ошибка счёта (лишнее/потерянное на границах групп).

## 2. Что сделано в v3

| Изменение | Зачем |
|---|---|
| Явная двухшаговая процедура: ШАГ 1 бренды+счёт (все правила подсчёта, наверху) → ШАГ 2 подвиды | Возвращает счёту приоритет v1; подвиды не мешают счёту |
| Правило сохранения: сумма front_facing_count групп бренда на полке = опорное число шага 1; «не сходится — пересчитай группы, опорное число не трогай» | Главный рычаг против дрейфа счёта при дроблении на подвиды |
| Восстановлено правило v1: «явно наш бренд, подвид не читается — ВСЁ РАВНО считай» + «неуверенность в подвиде не выбивает единицу из счёта» | Лечит недосчёт от строгости подвидов |
| 21 словесное описание подвидов урезано до списка канон-имён | Один источник визуальных признаков — справочник-PDF; конфликты текст↔картинка исчезают; промпт короче на ~40% |
| «НЕ ПУТАТЬ» сжат до 3 пунктов «ЧАСТЫЕ ОШИБКИ»; пара Буратино гранат ↔ Компотай вишневый явно помечена как ошибка БРЕНДА (проверка логотипа) | Адресует наблюдаемые ошибки, не раздувая промпт |
| Финальная фраза user-part: «сначала посчитай бренды по полкам (шаг 1), потом подвиды (шаг 2)» | Дублирует процедуру в последнем сообщении перед фото |

Канон-имена не тронуты — совпадают с `subtype_names_APPROVE.md` и подписями в `brands_catalog_new_2.pdf` буква в букву.

**Риск (обозначаю один раз):** без словесных описаний точность подвидов опирается только на PDF. Если регрессия покажет рост ошибок подвида — вернуть описания ТОЛЬКО для пар-близнецов, не весь блок.

## 3. Установка

1. Открыть ноду **«Gemini Vision (3.5-flash)»** → JSON Body → заменить всё содержимое на `gemini_vision_jsonBody_v3.json`, сохранив ведущий `=`.
2. **Обязательно то же самое в fallback-ноде «Gemini Vision (3-flash-preview)»** — иначе fallback работает по v2 и результаты регрессии несравнимы.
3. Проверить, что в file_data осталось `{{ $json.file_url }}` (колонка Config-листа). Внимание: в старом файле `gemini_vision_jsonBody_v2.json` было `$json.file_uri` — в живой ноде правильно `file_url`.
4. Смена systemInstruction сбрасывает implicit-кеш — первые запросы дороже/медленнее, это ожидаемо.

## 4. Проверка (регрессия — обязательна, это спринт-пункт №1)

Прогнать 14 фото из `Examples/` на v2 и v3 (одни и те же фото, обе модели не менять). Сравнивать:

1. Сумма front_facing_count по фото vs ручной подсчёт (главная метрика).
2. Строк с неверным брендом (включая пару Буратино гранат ↔ Компотай вишневый).
3. % ошибочных подвидов и % null-подвидов (null вырастет — это норм, ошибочный подвид хуже пустого).
4. Контроль сумм: по каждой полке сумма групп бренда одинакова в v2 и v3? Расхождения — кандидаты на ошибки v2.

Если счёт вернулся к уровню v1, а подвиды просели → вернуть описания близнецов (см. риск выше). Если счёт всё ещё хуже v1 → следующий рычаг: промежуточное поле в схеме (`brand_totals` по полкам ДО items + propertyOrdering) — структурное «рассуждение» при temperature 0; парсер его игнорирует, правок нод не нужно.
