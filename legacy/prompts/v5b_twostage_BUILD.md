## 0. Как это работает

```
Перевод фото в строку
        │
Каталог брендов: Config          ← теперь читает лист Catalog (22 строки)
        │
   Скан включён?  ←── ЕДИНСТВЕННЫЙ переключатель режимов (true/false)
   │true      │false
   ▼          │
Скан брендов: сборка             ЭТАП 1: «какие бренды на фото?»
   ▼          │                  (только фото + текст-приметы, без эталонов,
Gemini Скан (3.5-flash)           schema {brands:[enum]}, temp 0)
   ▼          │
Скан брендов: парсинг            любой сбой/пусто → brands=null
   ▼          ▼
Сборка запроса Gemini            ЭТАП 2: детальный запрос.
        │                        brands есть → эталоны ТОЛЬКО этих брендов;
        ▼                        brands=null → все 22 (= режим all-22)
Gemini Vision (3.5-flash) → … существующая цепочка без изменений
```

Правила деградации (фото не теряется никогда):

| Ситуация | Что происходит |
|---|---|
| Скан упал (HTTP/JSON) | brands=null → детальный этап со всеми 22 эталонами |
| Скан вернул пустой список | то же — страховка от ложного «ничего нет» (селфи/чек всё равно дадут 0 позиций на этапе 2) |
| Скан пропустил бренд | счёт НЕ страдает: промпт этапа 2 велит считать все 5 брендов; пострадает только подвид этого бренда (уйдёт в null) |
| Скан добавил лишний бренд | +несколько лишних эталонов в запросе, безвредно (скан специально смещён в сторону «сомневаешься — включай») |
| «Скан включён?» = false | чистый режим all-22, скан-нода не вызывается (нет лишних запросов) |

## 1. Предусловия (один раз)

1. **Лист `Catalog`** в spreadsheet «Vision Assistance Admins»: создай вкладку, в первую строку — 8 заголовков:
   `key | brand | canon_name | drive_file_id | file_url | mime_type | expires_at | updated_at`
2. **Папка Drive** с 22 эталонами — доступ «все, у кого есть ссылка». Структура любая из:
   - 5 папок по брендам, файлы `1.png…` внутри (как у тебя на десктопе) — филлер сматчит папка→бренд + номер→вкус;
   - одна папка с файлами-слагами (`aitea_malina.png`…) — матчинг по имени напрямую;
   - папки по брендам + слаги внутри — тоже ок (папка станет доп-проверкой бренда).
3. Больше НИЧЕГО не нужно: филлер работает от твоего Google-аккаунта (Apps Script), никаких API-включений и креденшлов.

## 2. Филлер манифеста — Apps Script (см. `catalog_filler_APPS_SCRIPT.md`)

⚠️ Первая версия (мини-WF `catalog_filler_WF.json`) отменена: Google Drive API не принимает API-ключи — «API keys are not supported by this API», OAuth-only, и включение Drive API в консоли это не чинит. Если успел импортировать — удали воркфлоу из n8n.

Замена: скрипт в спредшите Admins (Расширения → Apps Script), работает от твоего аккаунта — один диалог разрешений в браузере. Полный скрипт и 5 шагов установки — в `catalog_filler_APPS_SCRIPT.md`. Логика та же: листает папку и подпапки брендов → матчит файл→подвид (слаг ИЛИ папка+номер) → upsert 22 строк в Catalog по key (повторный запуск безопасен). Падает с понятной ошибкой, если: подвид без файла, один подвид на два файла, папка не распознана как бренд, конфликт «папка говорит одно, слаг другое». Не картинки (PDF и пр.) пропускает и перечисляет в предупреждениях.

⚠️ Если файлы матчились «папка+номер»: порядок вкусов AI TEA (1=малина … 9=персик-жасмин) — догадка из `wf2_catalog22_BUILD.md` §1.2. Филлер прямо напишет об этом в предупреждении. Селфчек (шаг 4) закрывает этот риск фактической проверкой.

## 3. WF-3 v2 — прогон

Вручную запусти свой WF-3 (каталог-аплоадер): все 22 строки Catalog должны получить `file_url`. Дальше он сам по расписанию 05:00 перезаливает (файлы Files API живут ~48 ч).

## 4. Селфчек каталога (catalog_selfcheck_WF.json) — ОБЯЗАТЕЛЬНО после первого прогона WF-3

Import from File → проверь креденшлы (Sheets + HTTP) → запусти. Один запрос к Gemini: все 22 эталона с подписями «key=…; заявлено: …», модель читает этикетку каждого и возвращает matches_declared. Вердикт в выводе ноды «Селфчек: вердикт»:
- ✅ «Каталог чист» — едем дальше;
- ❌ расхождения — отдельным item на каждое: какой key, что реально на этикетке. Правишь файлы/ID → WF-3 → селфчек заново.

Это единственное место, где «перепутал строку маппинга — каталог отравлен» ловится фактом, а не глазами. Гонять после любой пересборки каталога.

## 6. Протокол замера (A/B/C)

Я бы мерил в таком порядке — по одной переменной, это твоя же методология из фазового плана:

| Шаг | Режим | Что изолируем |
|---|---|---|
| C0 | текущий PDF-каталог (результаты уже есть с v3/v5-тестов) | бейзлайн |
| C1 | «Скан включён?» = **false** (all-22) | эффект «22 PNG с текст-метками вместо PDF» — это и есть замер шага 0 |
| C2 | «Скан включён?» = **true** | эффект фильтрации эталонов сканом |

Если сразу начать с C2 и станет лучше — не узнаешь, что сработало: новый каталог или фильтрация. C1→C2 это разделяет, стоит один лишний прогон той же пачки фото.

Метрики на одном наборе фото (Examples + твои живые кадры): сумма единиц vs ручной счёт; ошибки бренда; подвид верно / null / ошибочно; `_usage.cached_tokens` (в C1 префикс стабильный — кеш должен жить; в C2 префикс меняется от состава брендов — кеш будет хуже, это ожидаемо); латентность end-to-end (C2 = +1 запрос, ориентир +2–5 с).

В executions диагностика: у «Сборка запроса Gemini» в выводе `scan_brands` (null = шли все 22) и `refs_count`; у «Скан брендов: парсинг» — `scan_note`.

## 8. Честно про ожидания

Двухэтапность бьёт по ПОДВИДАМ (меньше эталонов-дистракторов в детальном запросе — та же логика, что «кроп против каталога одного бренда» из Visual RAG). По СЧЁТУ она не делает почти ничего: считает по-прежнему модель промптом, а недосчёт в плотных сценах — её системное свойство. Если после C1/C2 счёт всё ещё главная боль — следующий рычаг не промпт и не каталог, а шаг 1 из `vision_architecture_DETECTION.md`: боксы + счёт в Code-ноде. Благодаря тому, что тело запроса теперь собирается в одной Code-ноде, v6-детекция станет правкой одного места.
