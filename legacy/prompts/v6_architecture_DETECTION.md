# Архитектура распознавания: детекция вместо «посчитай промптом»
Проект BURATINO · 2026-07-15 · ответ на брейншторм Никиты (5 файлов каталога, два прохода, пересборка каталога)

---

## 1. Что говорит чужой опыт (главное)

1. **VLM плохо считают — это свойство, а не наш баг.** Исследования 2025–26: мультимодальные модели систематически НЕДОоценивают количество в плотных сценах (предобучение на «редких» картинках), сбой происходит на этапе перечисления, а не восприятия — модель «видит» объекты, но теряет их при связывании в число. Наши симптомы один в один. Вывод: сколько ни крути текст промпта, потолок близко.
2. **Индустрия shelf-аудита (Trax, Vispera, Neurolabs и т.д.) не просит модель считать.** Стандартный конвейер: (а) детекция — найти каждую единицу боксом; (б) классификация — каждый кроп сравнить с эталонной базой SKU; (в) фейсинги = число боксов, сгруппированных по SKU и полке. Счёт — детерминированная операция над списком боксов, не «мнение» модели. Width.ai таким конвейером дошли до 89% SKU-точности.
3. **Gemini умеет детекцию нативно.** Спец-навык spatial understanding: промпт вида «Detect the 2D bounding boxes of …» → массив `{box_2d: [y0,x0,y1,x1] (нормировано 0–1000), label}`. Это НЕ то же, что наш провалившийся v4: боксы — формат, под который модель специально дообучена, а не самодельная перепись.
4. **Fine-grained классификация против референсов — рабочий приём** (Visual RAG, CVPR 2025W): кроп + несколько эталонных картинок класса → VLM выбирает класс. Ключевое: задача «этот кроп против 5–9 эталонов ОДНОГО бренда» на порядок проще, чем «полка против 22 карточек всех брендов».

## 3. Целевая архитектура

```
Фото полки
   │
   ▼
ПРОХОД 1 · ДЕТЕКЦИЯ (Gemini, spatial understanding)
  вход: фото + компактный бренд-лист (1 файл: 5 обликов брендов)
  промпт: "Detect the 2D bounding boxes of каждой единицы переднего ряда
           брендов … . label = бренд. Задний ряд не включать."
  выход: [{box_2d, brand, shelf_index}]
   │
   ▼
CODE-НОДА (детерминированно, не модель):
  счёт = число боксов по (полка, бренд); сортировка по x → слева/центр/справа;
  дедуп пересекающихся боксов (IoU); суммы для отчёта
   │
   ▼
ПРОХОД 2 · ПОДВИДЫ (по одному запросу на ОБНАРУЖЕННЫЙ бренд)
  вход: фото + боксы единиц этого бренда + каталог ТОЛЬКО этого бренда (PNG)
  промпт: "Для каждого бокса определи подвид по каталогу. Не уверен — null."
  выход: подвид на каждый бокс
   │
   ▼
MERGE → items (те же колонки; счёт из прохода 1, подвиды из прохода 2)
```

Цена: 1 + число брендов на фото запросов (обычно 2–4 вместо 1). Латентность ×2–3. На нашем объёме — некритично; проход 2 можно слать параллельно по брендам.

Бонус, который даёт только эта схема: боксы можно отрисовать на фото и отправить агенту с карточкой аппрува (флоу №5 уже собран) — человек проверяет счёт глазами за секунды. И регрессия становится предметной: видно, КАКУЮ банку модель потеряла.

Каждый шаг замеряется на одном наборе фото: сумма единиц vs ручной счёт, ошибки бренда, подвиды верно/null/ошибка.

## 5. Риски и границы

1. Детекция в очень плотных рядах тоже не идеальна (SKU-110K существует именно потому, что это сложно) — но недосчёт детектора виден по боксам и лечится точечно, недосчёт «числом из промпта» — чёрный ящик.
2. box_2d нормирован 0–1000 — в Code-ноде пересчитать в пиксели при отрисовке/кропах, не забыть.
3. Два прохода = каталог подвидов уходит из прохода 1 совсем — бренд-лист должен быть самодостаточным для брендов (логотипы крупно).
4. Формат ответа детекции у Gemini «привычный» (`box_2d`, `label`) — не изобретать свои имена полей, модель дообучена под эти.

## 6. Хранение каталога: 22 файла по подвидам (решение 2026-07-15)

Гранулярность ХРАНЕНИЯ ≠ сколько слать в запрос. 22 отдельных файла — максимум гибкости: в конкретный запрос уходит ровно то подмножество, которое нужно этой стадии.

**Как слать в Gemini:** contents.parts — это массив, части чередуются: текст-метка → картинка → текст-метка → картинка… Каждый эталон предваряется своей меткой:

```json
{ "text": "Эталон подвида «AI TEA малина»:" },
{ "file_data": { "mime_type": "image/png", "file_uri": "<uri>" } },
{ "text": "Эталон подвида «AI TEA ревень»:" },
{ "file_data": { ... } }
```

Два системных выигрыша против PDF:
1. **Подпись становится текстом, а не пикселями.** Канон-имя эталона читается гарантированно — раньше оно зависело от разрешения растеризации PDF-страницы.
2. **Каждый эталон — в полном разрешении картинки**, без пережатия страницы с 4–5 карточками.

**Files API, не inline:** inline base64 упирается в лимит ~20 МБ на весь запрос, 22 фото могут не влезть; Files API — без этой проблемы, файлы живут ~48 ч (WF-3-перезаливка уже есть, расширить с 1 файла до 22 циклом), и статичный префикс из одних и тех же file_uri в одном порядке дружит с implicit-кешем. Лимит числа картинок на запрос у Gemini — сотни+, 22 не проблема (точную цифру для 3.5-flash смотреть в докax, нам не критично).

**Кто что получает по стадиям:**

| Стадия | Эталоны в запросе |
|---|---|
| Проход 1 (детекция брендов и счёт) | 0 файлов подвидов — только бренд-лист (1 файл, 5 обликов/лого) или вовсе текст. Минимум визуального контекста → всё внимание на фото |
| Проход 2 (подвиды бренда X) | Только 3–9 файлов бренда X, каждый с текст-меткой |
| Точечная перепроверка близнецов | Ровно 2 файла пары |
| «Все 22 в один запрос» | ❌ не делать — та же расфокусировка, что с PDF, только дороже |

**Правки инфраструктуры:** Config-лист → 22 строки (key=slug подвида, brand, file_url, mime_type); WF-3 → Loop по 22 файлам; сборка parts — в Code-ноде перед HTTP Request (динамический jsonBody вместо статичного шаблона; фильтр строк Config по бренду для прохода 2).

**Остаётся в силе:** студийные фото ≠ полка (ракурс, свет, ряд соседей) — если после внедрения подвиды всё ещё промахиваются, добавить к студийным по 1 полевому кадру на подвид.
