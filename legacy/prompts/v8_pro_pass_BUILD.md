# v8 — двойной проход: Flash боксирует, Pro определяет содержимое боксов

Альтернативная ветка архитектуры. Включается и выключается одной нодой, проход 1 не трогается.
Файл сниппета: `pro_pass_nodes.json` (4 ноды).

## 1. Почему так, а не «отдать Pro координаты»

Замер 03.08 на IMG_0644:

| | боксы | подвиды |
|---|---|---|
| Flash v7.4 | **53/53** | 50/53 |
| Pro 3.1 | 49/53 | **49/49** |

Боксы Pro сдвинуты вправо ровно на **+77/1000 по X** на всех пяти полках (Y и масштаб не меняются).
Отдать ему наши координаты нельзя: он смотрит в смещённой системе и будет описывать соседнюю единицу.
Но **порядок его подписей верен на всех полках** — он видит ряд правильно, ломается только эмиссия координат.

Поэтому проход 2 устроен так: **Pro не просят ничего локализовать.** Он получает то же фото,
тот же справочник эталонов и план «на полке 1 — 11 единиц, на полке 2 — 11, …», а возвращает
только упорядоченные слева направо списки подвидов. Мы кладём i-ю подпись на i-й бокс Flash.
Число единиц сообщаем сами — это заодно снимает его обрезание хвоста (в замере он терял
последние единицы на полках 3 и 4).

Если позже окажется, что порядок ненадёжен, следующая ступень — резать полосы по полкам
(Edit Image) и слать Pro каждую полосу отдельно. Пока это не нужно: на замере порядок совпал 5/5.

## 2. Ноды из сниппета

| нода | что делает |
|---|---|
| **Pro-проход включён?** (IF) | переключатель ветки. Выражение `{{ true }}` — ветка включена, `{{ false }}` — выключена, схема работает как v7.4 |
| **Сборка запроса Pro** (Code) | берёт `_detect.boxes_raw` прохода 1, группирует по полкам, сортирует слева направо, считает; собирает тело запроса: справочник эталонов + фото (base64 берётся из «Перевод фото в строку», повторно не качается) + план по полкам. Блок SUBTYPE — из v7.4, блока ПАР нет |
| **Gemini Pro (подвиды)** (HTTP) | `gemini-3.1-pro-preview:generateContent`, тот же креденшл, 3 ретрая, ошибка → обычный выход (чтобы упасть в фолбэк, а не уронить фото) |
| **Слияние подвидов** (Code) | накладывает подписи на боксы по порядку внутри полки и пересобирает `items` |

**Защита от тихого сдвига:** если длина списка Pro для полки ≠ числу боксов Flash на этой полке,
полка остаётся на подвидах Flash, а причина пишется в `_pro.detail`. Списки разной длины не зипуются
никогда — одна лишняя позиция молча сдвинула бы все подписи полки на единицу.

Диагностика в выводе: `_pro.shelves_applied`, `_pro.subtypes_changed`, `_pro.detail[]`
(с `count_seen` и флагом `count_mismatch`), `_pro.usage`.

## 3. Установка

1. Открыть `pro_pass_nodes.json`, скопировать содержимое **в буфер обмена и вставить на канву
   WF-2 (Ctrl+V)** — не через Import from File, иначе затрёт воркфлоу.
2. Перекоммутировать три связи:
   - **удалить** связь «Парсинг обработки Google Vision» → «Подготовка данных для занесения в таблицу»
     (связь «Парсинг» → «Обновление лога (Processed)» ОСТАВИТЬ);
   - «Парсинг обработки Google Vision» → **«Pro-проход включён?»**;
   - **«Слияние подвидов»** → «Подготовка данных для занесения в таблицу»;
   - **«Pro-проход включён?»** выход **false** → «Подготовка данных для занесения в таблицу».
3. Проверить, что у ноды «Gemini Pro (подвиды)» подтянулся креденшл `Google Vision Cloud API`.
   Если нет — выбрать вручную, тот же, что у «Gemini Vision (3.5-flash)».

## 4. Обязательная правка «Формирование результата»

Эта нода читает разбор по имени ноды, а не с входа, поэтому исправленные подвиды до карточки
агента сами не доедут. Заменить первую строку:

```javascript
const parsed = $('Парсинг обработки Google Vision').first().json;
```

на:

```javascript
let parsed = null;
try { const m = $('Слияние подвидов').first().json; if (m && m.items) parsed = m; } catch (e) {}
if (!parsed) parsed = $('Парсинг обработки Google Vision').first().json;
```

Работает в обоих режимах: ветка выключена → берётся проход 1.
«Подготовка данных» правки не требует, она читает `$input`.

## 5. Тест

1. **Ветка выключена** (`{{ false }}`) — прогнать IMG_0644, убедиться, что результат совпадает с v7.4
   (53 бокса, 50 верных подвидов). Это проверка, что перекоммутация ничего не сломала.
2. **Ветка включена** — тот же кадр, 2 прогона. Цель: **53/53 боксов и 53/53 подвидов**.
   Смотреть `_pro`: `shelves_applied` должно быть 5, `subtypes_changed` ≈ 3, `count_mismatch` — нигде.
3. **Фолбэк:** временно подставить в URL Pro несуществующую модель. Ожидание: фото не падает,
   подвиды остаются от Flash, в `_pro.detail` — «Pro не ответил».

## 6. Что держать в голове

- **Цена.** Проход 2 — это ещё ~55K prompt-токенов **по тарифу Pro** на каждое фото. Посчитай
  стоимость одного фото по `_pro.usage` и умножь на реальный поток, прежде чем раскатывать на всех агентов.
  Первый рычаг экономии, если дорого: убрать из запроса Pro справочник эталонов и проверить,
  держит ли он свои 49/49 без него — тогда префикс схлопнется в несколько тысяч токенов.
- **Кеш.** Префикс прохода 2 отличается от прохода 1 (другой system + план), так что implicit-кеш
  для него отдельный и первые прогоны будут без попадания.
- Порядок «слева направо» — договорённость между нашей сортировкой по `xmin` и перечислением Pro.
  На замере совпал на всех пяти полках, но это единственное неявное допущение схемы;
  флаг `count_mismatch` — ранний сигнал, что оно поехало.
