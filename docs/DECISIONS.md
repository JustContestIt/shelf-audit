# Архитектурные решения (ADR)

Формат: контекст → решение → альтернативы → последствия. Номера ADR упоминаются в коде (`grep -rn ADR-`).
Цифры взяты из [EVALS.md](../EVALS.md) и из истории проекта ([PROMPTS.md](PROMPTS.md), `evals/history/`).

---

## ADR-001. Оркестрация на LangGraph

**Контекст.** В n8n конвейер состоял из двух workflow: WF-2 на 33 узла и Main WF на 88 узлов. Логика была
размазана по Code-узлам, версионировать и тестировать её было трудно. Курс требует агентный фреймворк,
human-in-the-loop, трассировку и evals.

**Решение.** LangGraph 1.x, `StateGraph` с Pydantic-состоянием. Цикл проверки подвидов ограничен
(`max_verify_iterations = 2`). Остановка на `interrupt()` для проверки человеком, продолжение через
`Command(resume=…)`. Чекпойнты хранятся в Postgres.

**Альтернативы:**

- **CrewAI** — роли агентов с диалогом. Задача детерминированная: одна модель и две фиксированные стадии, «команда
  агентов» ничего не решает, а поток становится менее предсказуемым.
- **Parlant** — сделан для разговорных агентов с гайдлайнами, не для конвейера над картинкой.
- **Оставить n8n.** Нет unit-тестов, нет чекпойнтов с продолжением, нет интеграции с eval-раннером.
- **Голый Python.** Пришлось бы самим писать чекпойнты, interrupt и трассировку.

**Последствия.** Граф один и тот же для API, бота, MCP и eval-раннера. Узлы — чистые функции над состоянием,
их легко тестировать. Схема графа генерируется из кода (`/graph/mermaid`).

## ADR-002. Одно фото — один прогон, `thread_id = report_id`

**Контекст.** Агент шлёт альбом. Супервайзер может ответить через час. Пересъёмка относится к тому же отчёту.

**Решение.** Каждое фото — отдельный прогон. Альбом раскладывается на отчёты по фото, так же как в n8n.
Пересъёмка — ребро `human_review → validate_input` в том же треде (не больше 1 раза). Большие данные в
состояние не кладутся: фото хранится на диске, в состоянии только путь и sha256.

**Последствия.** Отчёт переживает рестарт API (PostgresSaver). Кэш ответов модели ключуется по sha фото.
Отчёт по «полке из двух фото» пока не собирается.

## ADR-003. Модель: gemini-3.5-flash, temperature 0, thinking по умолчанию, ULTRA_HIGH на фото

**Контекст.** Модель выбиралась в n8n по замерам (см. PROMPTS.md):

- Pro 3.1 точнее по подвидам (49/49), но теряет рамки (49/53) и сдвигает их на +77/1000 по x;
- 3.5-flash лучше 3-preview и 3.1-flash-lite;
- без thinking качество падает в разы, при этом thinking занимает ~90 из ~97 с на фото;
- ULTRA_HIGH прироста не дал, но и не мешает.

**Решение.** Проход 1 и проход 2 идут на `gemini-3.5-flash`, `temperature=0`, thinking по умолчанию.
`media_resolution=ULTRA_HIGH` задаётся только частью с целевым фото, эталоны идут с разрешением по умолчанию.

**Альтернативы.** Отдельный Pro на проход 2 (как в v8) дороже и на полке 1 IMG_0643 дал 13/20 против 17/20 у Flash:
границы групп «плыли». Позже проход 2 перевели на Flash (v9-groups), но и в таком виде на AITEA_5SHELF он ухудшал
результат в 5 из 6 прогонов (ADR-007). GPT-5.6 через OpenRouter оставлен как fallback и рука A/B-3.

**Последствия.** Температура, thinking, top_p и max_output_tokens заданы в `evals/configs/hp_*.yaml` и ждут
живого ключа. Google советует 1.0 для Gemini 3 — это как раз проверяется.

## ADR-004. REST `generateContent` с телом как в n8n, а не SDK google-genai

**Контекст.** Любое отличие тела запроса от боевого (порядок частей, `file_data` против `inline_data`,
per-part `media_resolution`, `response_schema`) меняет ответы модели. Тогда сравнение «до и после» переноса
становится нечестным.

**Решение.** Тело собирается функциями `app/vision/requests.py`. Тест прогоняет оригинальный JS узла n8n в Node
на тех же входах и сравнивает тела байт в байт (`tests/test_prompts.py`, `tests/test_js_parity.py`).
Клиент — httpx, с ретраями и таймаутами.

**Альтернативы.** SDK `google-genai`: удобнее, но скрывает сериализацию, а per-part `media_resolution` в нём
появился не сразу. Его можно подставить за тем же интерфейсом `generate()`.

**Последствия.** Записанные ответы n8n валидны как кэш для нового графа. Именно на этом построены метрики
«до переноса».

## ADR-005. Цепочка fallback: 3.5-flash → 3-flash-preview → OpenRouter

**Контекст.** На демо 31.08 были 429 и 503. В n8n fallback-узел жил со старым промптом v4 и молча портил
результат.

**Решение.** `FallbackChain` из `DETECT_MODELS` / `VERIFY_MODELS` (+ OpenRouter, если задан). Для всех моделей
одно и то же тело и один промпт. Какая модель ответила, пишется в `llm_calls[].model` и `fallback_from`.
Если проход 2 недоступен, берётся top-1 ансамбля RAG с пометкой `needs_review`. Если недоступен проход 1,
отчёт получает статус `failed` с флагом. Тест «выключили основную» — `test_primary_model_down_falls_back_to_next`
в `test_graph.py`.

**Последствия.** Для демо есть ещё и `LLM_MODE=replay`: записанные ответы на случай, когда недоступно всё.

## ADR-006. pgvector, а не Qdrant

**Контекст.** Эталонов 150–300, запросов — единицы в минуту.

**Решение.** Таблица `ref_embeddings` в том же Postgres, где отчёты и чекпойнты LangGraph. Индекс HNSW по
SigLIP (cosine), рядом HSV-вектор. Офлайн используется снимок `.npz`: тот же top-3 на 129 из 129 запросов (`evals/rag_parity.py`).

**Альтернативы:**

- **Qdrant / Chroma** — лишний контейнер без выигрыша, скорость ANN на 188 векторах не важна;
- **только numpy** — нет общего хранилища для API и джобов.

## ADR-007. Проход 2 — только по неуверенным группам и правит только их

**Контекст.** В n8n (v9-groups) проход 2 называл каждую группу заново. На AITEA_5SHELF 01.09 он ухудшил
результат в 5 из 6 прогонов: медиана ошибок была 3, стала 5. На записанных прогонах это подтверждается —
pass 1 без прохода 2 точнее по вкусу во всех трёх сериях. Помогал проход 2 только в «розовой зоне» AI TEA
(персик, малина, клубника, гуава, помело, ревень) и на группах без вкуса.

**Решение.** `PASS2_MODE=gate`: в проход 2 идут только неуверенные группы — AI TEA из розовой зоны или
без вкуса. Правки применяются только к ним (`merge_verify(targets=…)`), уверенные имена прохода 1 не трогаются.
Режим `check`: для неуверенных групп работает только RAG с проверкой «свой / чужой», без LLM.

**Альтернативы:**

- `always` — как в n8n;
- `off` — только проход 1;
- гейт по confidence — не откалиброван (№5, №32).

**Последствия и данные** (replay, [EVALS.md](../EVALS.md#что-из-этого-следует)). Гейт снижает вред прохода 2, но
не убирает его. Лучшая комбинация на записанных ответах — `check`, то есть проход 1 плюс проверка «свой / чужой».
По умолчанию пока стоит `gate`: на живом ключе проход 2 получит другие эталоны (top-k вместо 46), и решение
принимается по A/B-1 и A/B-2. Если живые прогоны это подтвердят, переключаемся на `PASS2_MODE=check`: без
второго вызова модели минус 32–35 % стоимости и примерно минус 45 с на фото.

## ADR-008. Визуальный RAG: SigLIP + HSV, top-k эталонов в проход 2

**Контекст.** Эксперимент 24.08 на 129 размеченных банках:

| метод | точность |
|---|---|
| SigLIP | 79 % |
| DINOv2 | 47 % |
| CLIP | 32 % |
| HSV-гистограмма | 84 % |
| ансамбль SigLIP + HSV | **93 %** |

Лучший эмбеддер в одиночку хуже прохода 1 на IMG_0643: 55 против 62 из 65. Значит, заменить проход 2
эмбеддингами нельзя, а сузить ими выбор эталонов можно.

**Решение.** Кропы неуверенной группы (до 3 шт., 384 px) → z(SigLIP) + z(HSV) → top-3 SKU внутри бренда. В проход 2
идут только их эталоны, а не все 46.

**Последствия.** Воспроизведено: 120/129 на наборе эталонов 24.08. С полным каталогом, фильтром по бренду и без
ревеня получилось 125/129 (96,9 %), recall@3 = 100 %. То есть верный эталон всегда среди отправленных. Эффект на
качество прохода 2 — это A/B-1, ждёт ключа.

## ADR-009. Исключить «AI TEA ревень» из enum и эталонов

**Контекст.** Полевых фото ревеня нет, SKU, по словам заказчика, в продаже почти не встречается. При этом
модель уводила в ревень персик: ×5 на IMG_0643.

**Решение.** `EXCLUDE_KEYS=["aitea_reven"]` в обоих проходах и в RAG, как в n8n с 31.08. В n8n
эталонов стало 49 → 47, подвидов 22 → 21. У нас из 48 активных строк остаётся 46.

**Последствия.** Если ревень всё-таки стоит на полке, он станет «не опознано» или уйдёт в соседний вкус. Вопрос
заказчику №11 открыт. Возврат — одна строка в `.env`.

## ADR-010. Активные эталоны = каталог n8n на 31.08, с настоящими макетами ПЭТ

**Контекст.** В n8n три строки `*__pet05_ru` ссылались на полевые фото банок, а не на макеты ПЭТ 0,5 л.
Это «ложные дубли» из №31.

**Решение.** `app/catalog/active_refs.yaml` — те же 48 строк, что в Data Table `brand_catalog`. Картинки из
`refs_1280/`, три ПЭТ-строки указывают на реальные макеты.

**Последствия.** Проход 1 отличается от n8n ровно тремя картинками. В replay это не видно (ответы записаны
заранее), на живом ключе сравнение даёт baseline `detect_v7.5` против n8n-записей.

## ADR-011. Проверка «свой / чужой» по SigLIP

**Контекст.** Банки конкурента с похожей этикеткой получали подпись AI TEA и попадали в счёт.

- **Данные.** Contamination 20 единиц за 9 прогонов на IMG_0644. `ЧУЖОЙ` в n8n не срабатывал (№28).
- **Эксперимент 24.08.** Порог max-sim 0,70 пропускает около 3 % чужих.

**Решение.** Если у группы нашего бренда нет вкуса, а максимальное сходство SigLIP с нашими эталонами
`< 0,70`, её единицы исключаются из счёта. В отчёте они видны как «похожи на чужой товар», супервайзер может их
вернуть. `FOREIGN_ACTION=flag` только помечает.

**Последствия.**

- На v7.4 contamination снизилась с 20 до 4, полок с точным счётом стало 91,1 % вместо 82,2 %.
- На v7.5 остался случай, который не разделяется: серебристая банка конкурента имеет сходство 0,717, а самая
  непохожая настоящая AI TEA — 0,718. Порог ниже даст ложные исключения. Нужны полевые эталоны конкурента.

## ADR-012. Собственный eval-фреймворк с кэшем ответов, без LLM-судьи

**Контекст.** Эталон точный: рамки, счёт, позиционная последовательность вкусов по полке. Каждый прогон
стоит денег, а оценка «на глаз» по одному прогону обманывала (σ ошибок подвида 0,6–2,8 между прогонами).

**Решение:**

- **Скорер.** Позиционное выравнивание внутри полки, обобщение `bench/score_runs.py` (сверено на записанных
  прогонах).
- **Метрики.** 7 штук и срезы по тегам edge cases.
- **Кэш.** Ответы модели кэшируются по `hash(фото + промпт + эталоны + генконфиг + соль повтора)`.
- **Replay.** Записанные ответы n8n прогоняются через новый граф.
- **LangSmith.** Необязательная выгрузка результатов как experiment.

**Альтернативы.** LLM-as-judge для счёта только добавил бы шум. Уместен он будет для текстовых ответов
ассистента супервайзера (faithfulness), когда такой появится.

## ADR-013. Данные заказчика вне git, секреты под gitleaks

**Решение:**

- **Данные.** `data/` в `.gitignore`. Данные копирует `fetch_data.py` по явному allow-list с deny-списком
  (`_to_delete`, `archive`, ключи и т. д.) и пишет `MANIFEST.json` с sha256.
- **Секреты.** Gitleaks стоит в pre-commit и CI, есть свои правила для токенов Telegram, Google и OpenRouter.
- **Экспорты n8n.** Кладутся в `legacy/n8n/` только после `clean_exports.py`: токены, chat_id, credential id и
  pinData вырезаются.
- **История промптов.** Импортируется с редактурой: chat_id и названия магазинов из тестовых кадров убираются.

**Последствия.** CI с живыми кадрами требует приватного архива (`DATA_ARCHIVE_URL`). Без него идут только тесты
скореров.

## ADR-014. Веб-кабинет обязателен, бот — канал агента

**Контекст.** Одного Telegram-бота могут не засчитать как веб- или мобильное приложение. Супервайзер сейчас
сверяет отчёты глазами в Google Sheets.

**Решение.**

- **Кабинет.** React-кабинет супервайзера: очередь, рамки на фото (цвет = подвид, пунктир = `needs_review`),
  правка строки, пересъёмка, отчёты по точкам, evals, схема графа.
- **Бот.** Бот на aiogram — тонкий клиент того же API. Авторизация упрощённая, по телефону: как в n8n, но
  номер нормализуется.

**Последствия.** Роли в API сейчас сводятся к общему токену. Разделение ролей агент / супервайзер / админ — бонус,
в бэклоге.

## ADR-015. MCP на standalone `fastmcp`, Skill поверх MCP

**Контекст.** В `mcp` 2.x встроенный FastMCP переименован и урезан, а standalone `fastmcp` умеет stdio и
streamable HTTP одним вызовом.

**Решение.**

- **MCP.** `fastmcp` 4.x, 4 tool'а поверх HTTP API. Своей логики у MCP нет.
- **Skill.** `shelf-audit-report` собирает xlsx из результатов tool'ов: «Сводка» считается формулами, а не
  значениями, чтобы заказчик видел, откуда число.

## ADR-016. Guardrails: сначала детерминированные проверки, LLM — по флагу

**Контекст.** Самые частые проблемы входа — смазанное фото, скрин вместо фото, фото с 400 px, PDF вместо
картинки. Их ловят дешёвые проверки. «Не полка» (каталог, макет, чек) требует модели.

**Решение.**

- **Всегда:** размер, формат, разрешение, блюр, pHash.
- **По флагу:** LLM-проверка «это полка?» (`SHELF_CHECK_LLM`).
- **Инъекции.** Текст-инъекция на фото не опасна по построению: счёт считается по рамкам, а не по тексту
  ответа. Кадр с надписью «посчитай 100 банок» должен пройти guardrails.

**Последствия.** Офлайн precision 1,0, recall 0,64. Все 9 детерминированных негативов пойманы, 16 настоящих полок
ни разу не отклонены. Каталог и макеты ловятся только LLM-проверкой.
